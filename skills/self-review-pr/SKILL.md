# Self-Review PR

A workflow for reviewing your own PR before marking it ready. Invoked when I say "self-review" or "review before shipping."

The preferred technique is a read-only subagent to reduce confirmation bias. When the host has no subagent capability, perform a clearly identified fresh-context second pass and disclose that limitation.

## Authority

The review and any local Markdown artifact are read-only with respect to repository source and GitHub. If the request already authorizes addressing valid findings, apply those local fixes after recording the independent review; otherwise report the findings and wait for the user's decision. `chat only` and `no artifact` change only delivery, but an explicit `do not write files` or `do not modify files` instruction overrides local-fix authority and prohibits every local file write. Create commits or mutate the remote PR only when those actions are separately authorized.

## Steps

1. Gather a fresh PR snapshot: record the PR URL, title, description, commit history, and both SHAs. Accept a supplied complete immutable snapshot without remote lookup. If supplied capability context explicitly records that the canonical pull-request identity and all supported evidence routes are unavailable, stop immediately before repository discovery. Request the canonical repository and pull-request number or URL, plus one usable evidence route: a complete immutable snapshot, the exact local checkout, or an authenticated supported pull-request read interface. Otherwise, use the identity from the prompt or retained task state, or resolve it through only the exact current checkout or one authenticated supported pull-request read interface. Resolve the recorded SHAs through those same bounded routes, then inspect the merge-base diff and full changed source. When reviewing unpushed local commits, use the verified local `HEAD` as the candidate after pinning the remote base, and derive scope locally. Check CI separately. If identity, revisions, and source are verified but discussion access is incomplete, continue with the accessible evidence and label the review partial. Otherwise, if neither evidence route can verify required PR or review state, stop after those checks and report the missing capability; do not search for alternate clients or unrelated repository metadata, enumerate unrelated local files, try unauthenticated web clients, or retry network routes. Re-read both SHAs before concluding and restart if either changed.
2. Check previous feedback before final synthesis. Read review bodies, inline threads and replies, and PR conversation comments through all available pages, including resolved and outdated threads. Assess each actionable concern against the pinned code, independently of GitHub thread state. Carry its original link, current assessment, and remaining change, reply, or verification into delivery. An open thread may already be fixed; a resolved or outdated one may still need work. An author's "fixed" reply alone is not proof. Report incomplete discussion access without claiming all feedback is addressed. Refresh this assessment before delivery. Keep earlier feedback out of the independent agent's first pass, then deduplicate its findings against that feedback.
3. Load `review-simplicity` and require its deletion-first baseline for the same snapshot even when simplification was not requested. Launch a read-only subagent with the captured context when available. Otherwise, start a fresh review pass without relying on the implementation rationale. Cover correctness, accessibility, consistency, simplicity, completeness, risks, and suggestions; an explicit no-findings simplicity result is valid.
4. Use the `draft-review-comment` skill for delivery, including its full-review format with Overall, Previous feedback, and Actions and suggested comments. No new findings does not mean earlier feedback is addressed. Return comments in chat without creating or opening a local file for `chat only`, `no artifact`, `do not write files`, or `do not modify files`; otherwise write the self-review to `<pr-number>-self-review.md` in the OS temporary directory, then open it when supported or return the path. Use exact file paths and line ranges for inline findings, file paths for file-level findings, and no fabricated location for general findings.
5. When local fixes were not already requested, let me decide what to act on.
6. When local fixes were requested before or after the review and no explicit no-write instruction revoked that authority, implement each accepted finding in a coherent batch. Prefer simple, direct solutions. Commit only if the user also requested commits.
7. Run the project's relevant verification suite after all fixes, then report the review output, any changed files, and remaining actions that still require authorization.
